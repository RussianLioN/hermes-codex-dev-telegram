## Purpose

Автоматически сохранять минимальные зашифрованные данные для восстановления проектов вне сервера через GitHub, без часовых полных архивов и без подмены проверки загрузки проверкой восстановления.

## ADDED Requirements

### Requirement: BACK-01 Changed-only encrypted offsite packages
Система SHALL автоматически отправлять компактные пакеты только изменившихся проектов после завершения этапа и перед обслуживанием, с суточной страховочной проверкой и объединением близких событий. Неизменившийся набор SHALL пропускать отправку. Уже доступные GitHub commits SHALL заменять повторный архив кода при гарантированной достижимости. Пакет SHALL сохранять необходимые unpublished commits, tracked diff, разрешённые untracked files, checkpoints и приватное runtime-состояние согласованного snapshot. Credentials, images, зависимости, caches и восстанавливаемый индекс SHALL исключаться. Шифрование SHALL использовать public key на сервере и private key только у владельца вне сервера/GitHub; создание backup не вызывает LLM.

#### Scenario: Only one project changed
- **WHEN** страховочная проверка видит изменение проекта A и отсутствие изменения B
- **THEN** отправляется только новый зашифрованный пакет A, а backup B не создаётся повторно

#### Scenario: Unpublished work
- **WHEN** работа содержит неотправленный commit и новый файл вне index
- **THEN** разрешённые данные включаются в snapshot и manifest; восстановление не ограничивается одним git diff и не требует недостижимого commit

#### Scenario: Concurrent writes
- **WHEN** задача меняет файлы или БД во время создания копии
- **THEN** используется согласованная граница snapshot либо операция безопасно повторяется; смешанная копия не отмечается успешной

#### Scenario: Credential embedded in checkpoint
- **WHEN** разрешённый файл checkpoint или журнал содержит распознаваемый credential, включая искусственный секрет негативного теста
- **THEN** до упаковки значение исключается или редактируется; при сомнении пакет блокируется с безопасным уведомлением без раскрытия значения. Проверяется содержимое выбранных файлов, а не только исключение auth-файлов; эвристика не выдаётся за гарантию распознавания любого секрета

### Requirement: BACK-02 GitHub storage and readback gate
Off-host storage SHALL использовать отдельный приватный RussianLioN/agent-backups с настраиваемым owner. Releases assets SHALL оставаться кандидатом до документальной проверки допустимости и лимитов; при несовместимости SHALL требоваться решение владельца, без платного сервиса или бесконечного коммита бинарных архивов в Git. Backup SHALL иметь ID, manifest, checksum, ссылки на commits/dependencies и readback точного удалённого объекта. Неуспех отправки SHALL сохранять локальную копию и возраст последнего успешного off-host backup, сообщать через Telegram и не считаться соблюдением суточного RPO.

#### Scenario: Upload response lost
- **WHEN** ответ GitHub потерян после отправки
- **THEN** система сверяет точный объект/ID/checksum до retry, не помечает успех только по факту запуска и не создаёт бессистемные дубликаты

### Requirement: BACK-03 Owner-attested restoration and protected retention
Владелец SHALL вручную запускать локальную restore-check команду: скачать выбранный пакет, расшифровать в отдельный каталог, проверить manifest/checksums/достижимость зависимостей без исполнения кода и перезаписи проектов. Результат SHALL передаваться через штатный Telegram с backup ID/checksum/result и приниматься только от владельца для точного объекта. Это SHALL называться owner attestation, не независимой серверной проверкой. Копии старше 30 дней SHALL удаляться автоматически только при наличии более новой verified-on-restore копии того же owner/project scope с подтверждённым покрытием заменяемых данных. Для каждой независимой области, включая общую память владельца, последняя проверенная копия и все её зависимости SHALL сохраняться независимо от возраста. Проверенная копия проекта B MUST NOT разрешать удаление последней восстановимой копии A. Проверка eligibility и удаление SHALL исключать гонки и повторно сверять ссылки. Без проверки SHALL сохраняться копии и отправляться уведомление.

#### Scenario: Retention without restoration evidence
- **WHEN** пакет старше 30 дней, но нет более новой проверенной копии
- **THEN** он не удаляется ради освобождения места, владелец получает предупреждение

#### Scenario: Spoofed or mismatched report
- **WHEN** отчёт прислан не владельцем либо ID/checksum не соответствует сохранённому объекту
- **THEN** статус restoration не меняется и удаление старых копий не разрешается

#### Scenario: Restore dependency retained
- **WHEN** новый проверенный пакет ссылается на commit или другую часть backup
- **THEN** retention сохраняет эту зависимость и не удаляет её только из-за возраста или удаления task branch

#### Scenario: Different project backup
- **WHEN** новая проверенная копия содержит только проект B, а копия A старше 30 дней
- **THEN** копия A не становится eligible только из-за успеха B; проверка покрытия выполняется отдельно для каждой owner/project области
