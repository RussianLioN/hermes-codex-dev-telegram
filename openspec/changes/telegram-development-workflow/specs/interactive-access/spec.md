## Purpose

Предоставлять владельцу обычный интерактивный Codex CLI по SSH внутри переиспользуемого контейнера проекта, не перехватывая автоматические задачи и не теряя ручную сессию при обрыве соединения.

## ADDED Requirements

### Requirement: SSH-01 Independent scoped interactive Codex
Система SHALL предоставлять авторизованному владельцу отдельную обычную интерактивную Codex CLI сессию в нужном project container с автоматической загрузкой актуального проектного контекста по MEM-12. Ручная сессия SHALL быть независима от Hermes-launched задачи, иметь отдельную identity и writer worktree/branch при параллельной работе. Захват текущей автоматической сессии SHALL NOT быть необходимым для ручного доступа. Границы ENV-01 и TG-05 SHALL применяться к обоим способам запуска; настройки SSH access и инфраструктуры SHALL меняться только после exact owner approval через Telegram.

#### Scenario: Open manual session alongside automation
- **WHEN** владелец подключается по SSH к разрешённому проекту с уже работающей Hermes-задачей
- **THEN** обычный интерактивный Codex запускается в том же project container, но отдельной сессии/worktree/ветке с актуальным контекстом; автоматическая задача не перехватывается и не прерывается

#### Scenario: Unknown project or unauthorized access
- **WHEN** нет однозначного разрешённого project binding или SSH identity не допущена к проекту
- **THEN** запуск отклоняется до доступа к файлам/истории; нет fallback в host shell с расширенными правами

#### Scenario: Concurrent integration conflict
- **WHEN** ручная и автоматическая ветки меняют один участок кода
- **THEN** интеграция выполняется отдельно и последовательно; конфликт не затирает ни одну работу, а объединённый candidate проходит повторные проверки до приёмки

### Requirement: SSH-02 Disconnect-safe session continuity
Разрыв SSH при живых host, project container и процессе Codex SHALL NOT завершать ручную сессию или запускать её копию. При reconnect авторизованный владелец SHALL возвращаться в ту же ручную сессию с её состоянием и выводом. Наличие нескольких сессий SHALL требовать однозначного выбора identity, не случайного attach к другому проекту. Завершение процесса или разрушение контейнера SHALL отличаться от транспортного disconnect: система SHALL сообщать о прекращении прежней сессии и восстанавливать сохранённые данные/контекст при новом разрешённом запуске, не обещая непрерывность погибшего процесса.

#### Scenario: SSH drops and reconnects
- **WHEN** SSH-соединение оборвалось во время живой ручной сессии, а владелец подключился снова
- **THEN** прежний Codex продолжает работу и reconnect возвращает к той же session identity, worktree и выводу без дублирующего запуска

#### Scenario: Codex died while disconnected
- **WHEN** при reconnect подтверждено, что прежний Codex завершился
- **THEN** владелец получает точный статус завершения; система не выдаёт новую сессию за прежнюю, а новый разрешённый запуск восстанавливает историю/checkpoint по MEM-12 без слепого повтора внешних действий

#### Scenario: Container destroyed while disconnected
- **WHEN** project container удалён между disconnect и reconnect
- **THEN** прежняя process session не объявляется сохранившейся; после разрешённого пересоздания тот же project storage доступен, новый запуск явно отделён от прежнего и получает восстановленный контекст
